# 부하 테스트 & 서버측 모니터링 계측 설계

> 부하 테스트(더미 클라이언트로 동시 접속을 늘려가며 서버 한계를 찾는 시험)에 들어가기 전,
> "무엇을·어떻게·어디까지" 측정할지 못 박아 둔 설계 문서. 아직 계측 코드는 미구현(설계 단계).
>
> 관련 코드: `Server\LoadTester\` (더미 클라), `Server\MMORPG_GameServer\` (계측 대상)

---

## 1. 부하 테스트 방법론 — "감"이 아니라 "절차"

### 본질
부하 테스트의 본질은 **동시 접속 수를 올려가며 병목(가장 먼저 막히는 지점)을 찾고, 그 해소법을 제시하는 반복 과정**이다. 단발 숫자("5000명 찍었다")가 아니라 **측정 → 병목 식별 → 가설 → 개선 → 재측정** 루프와 그 사이의 before/after 차이가 가치다.

막연해지지 않게 못 박을 것:

- **(a) 기준(SLO)을 먼저 정의** — "병목/실패"의 기준을 미리 숫자로 정해야 knee point(꺾이는 지점)를 "객관적 사실"로 말할 수 있다. 안 정하면 "느려진 것 같다" 수준에 머문다.
- **(b) 가치는 루프와 델타** — 측정→식별→가설→개선→재측정의 흐름과 before/after 차이가 핵심.
- **(c) 병목은 옮겨다닌다** — fan-out(패킷 1개를 주변 여러 명에게 복제해 뿌리는 확산 전송)을 풀면 락 경합으로, 그 다음엔 DB 입출력으로 병목이 이동한다. 이 단계별 이동을 보여주는 것이 시스템을 이해했다는 증거.
- **(d) 해소법이 꼭 코드 최적화는 아니다** — "단일 머신 한계는 여기까지, 그 이상은 수평 확장(서버를 여러 대로 나누는 샤딩/멀티월드)으로 넘긴다"도 정당한 결론. 단, 측정으로 한계를 입증한 뒤 아키텍처로 넘겨야 한다.
- **(e) 측정 환경 오염 통제** — 더미 클라와 서버가 같은 PC에 있으면 자원 경쟁 때문에 숫자가 거짓말을 한다(이미 이동 보간 작업에서 클럭 왜곡을 겪음). **네트워크 지표는 봇/서버를 별도 머신으로 분리 필수.** 분리가 어려우면 "절대치는 보정 대상이고, 보는 건 상대 추세(knee 위치)"라고 명시.

### 지표 두 부류 — 합격선 vs 진단

- **(A) 합격선 지표 (gate, 통과/실패):** 절대 기준을 미리 정한다.
  - **프레임 = 초당 40회 = 25ms**가 구조가 강제하는 기준(지속적으로/p99 기준으로 넘으면 실패, 단발 튐은 OK).
  - 게임이면 요청→응답 총지연도 체감선으로 둔다.
- **(B) 진단 지표 (diagnostic):** 프로토콜 개당 처리 시간, 락 진입 전후 대기 등.
  - **합격선을 정할 수 없고 정해서도 안 된다** — 절대 숫자에 근거가 없다(0.3ms든 2ms든 그 자체론 의미 없음).
  - **베이스라인이 기준**: 저부하(10/100명) 정상값 대비 **몇 배 뛰는가 + 어디서 꺾이는가(곡선 모양)**로 읽는다. knee 자체가 결론.
- **관계:** (B)는 독립 합격선이 불필요하다. (A)가 깨졌을 때 "왜"를 설명하는 증인이다.
  - 예: 프레임 25ms 초과(A=실패 확정) → 핸들러 순수 처리 시간은 평평한데 락 대기가 폭발(B=원인) → 패킷이 그룹을 점유해 틱을 밀어냄(결론). **판정관은 (A), 증인이 (B).**

### 테스트 시간 — 종목별로 다름

- **램프(knee 찾기):** 달력 시간이 아니라 "단계당 평형 도달 + 표본 충분"이 기준. 워밍업 수십 초 → 단계당 3~5분 유지(p99 표본 확보) → 동접 단계별 반복. 전체 약 **1~2시간**이면 곡선이 다 나온다.
- **내구성(soak, 장시간):** 일주일 무중단은 부하 테스트엔 무의미한 다른 종목. 포폴엔 일주일은 과하다.
  - **knee의 70~80% 부하로 12~24시간** 돌려 **추세 기울기**를 본다(메모리/지연/큐 깊이/핸들 수가 우상향 드리프트하면 누수·단편화·적체). 평평하면 안정성 입증 완료.
  - 일주일은 24h 기울기 외삽으로 대체 가능(한계효용 없음).
  - **soak가 특히 잡아줄 것:** DB 연결 재접속 / `wait_timeout`(유휴 연결이 끊기는 현상)은 짧은 부하론 안 나오고 몇 시간 흘러야 터진다.
- **권장 조합:** 램프 1~2h(knee) + soak 12~24h(안정성). 발표는 "24h 평평 그래프 + knee 곡선"이 "일주일 돌림"보다 방어가 강하다.

### 측정 단계 파이프라인
측정이 목적이 아니라 "X에서 터짐 → 원인 Z → 해결 → Y"라는 루프를 만드는 것이 목적.

0. 계측 심기 + 환경 분리(네트워크는 별도 머신 필수) + SLO 못 박기("터짐"의 정의: 프레임 25ms 지속 초과 / 총지연 p99)
1. **베이스라인(10~100명):** 도구·오탐 검증 + 진단 지표 기준값 확보
2. **램프(단계당 3~5분 유지):** 합격선 넘는 동접 = X(knee). 그래프 = 지표 vs 동접
3. **원인 귀속:** 3개 도메인 진단 지표를 같은 시간축에 겹쳐, **먼저 꺾인 도메인 + 구간**을 지목 = Z(인과 순서)
4. **해결:** 바로 되는 건 적용 / 오래 걸리는 건(DB 채널 등) 설계 제안
5. **재측정:** 새 knee = Y, **before/after 델타 = 발표 센터피스**
6. **soak 12~24h(knee 70~80%):** 기울기로 안정성 확인
7. **서사 정리 + 한계 정직하게**(예: 아이템 복사 탐지 불가 등)

추가 확정 지표:
- **OnUpdate 틱 주기 준수** (서버 로직 1순위 게이트)
- **코어별 CPU 사용률** — 전체 집계는 단일 코어 포화를 숨겨 단일 스레드 병목을 놓침
- **초당 세그먼트 수(segments/sec)** — 바이트가 아니라 패킷 수가 손실의 핵심
- **수신 큐는 없음** → 밀린 일감이 **락 대기로 간다**. 락 대기를 backpressure(밀린 부하가 역류하는 압력)의 본체로 격상. 발산하면 서버 로직 knee.

## 2. 서버측 모니터링 계측 설계

목표 = 부하가 어디에 걸리는지 짚어내기.

### 부하 3분할: DB / 네트워크 / 서버 로직

- **DB:** 큐가 발산(줄지 않고 우상향)하는 것이 병목 신호. 쿼리 p99·1초 초과 쿼리를 파일 로그.
- **네트워크:** segments/sec(바이트 아닌 패킷 수가 손실 핵심)·재전송률·RTT·Send IO 완료 수.
  - **단, 실측은 봇/서버 별도 머신 필수** — 루프백(같은 PC)이면 재전송 ≈ 0이라 무의미.
- **서버 로직:** 락 대기 + 핸들러 구간 타이머 + **OnUpdate 틱 주기 준수(start~start 간격 vs 25ms, 1순위 게이트)**.

### 모니터링 대상
- 전체 + 프로토콜별 **초당 Req/Res** (타입별 원자 카운터를 모니터 스레드가 1초마다 차분).
  - Res는 확산 전송 때문에 Req보다 크다 → **확산 배수(보낸/받은 비율)**도 같이 기록.
- **DBJobQueue 깊이** (모니터 틱에서 샘플링).

### 프로토콜 처리 시간 = 3시점으로 분리 (핵심)
- **원안의 문제:** OnRecv 직전 시각 → 핸들러 종료 시각의 차이만 재면 **핸들러 CPU 실행 시간만** 잡힌다.
- 락 기반 그룹에서 부하가 차오를 때 폭발하는 건 핸들러 시간이 아니라 **큐 대기 시간(= 그룹 배타 락 대기)**이다. 포화를 넘으면 처리 시간은 평평하고, 큐 대기가 수직 상승 = knee point 신호.
- **해결: 3시점.**
  - `t_enqueue`(수신/큐 삽입) / `t_start`(핸들러 시작) / `t_end`(종료)
  - 큐 대기 = `t_start - t_enqueue`, 처리 = `t_end - t_start`, 총지연 = `t_end - t_enqueue`
  - **enqueue 시점 추가가 제일 중요** — 안 하면 병목 그림을 통째로 놓친다.

### OnUpdate 프레임 측정
- 락 전 `t0` / 락 잡은 직후 `t1` / 작업 끝 `t2`. **분리 필수**(합치면 작업이 무거운 건지 패킷에 점유당한 건지 구분 불가).
  - `t1 - t0` = 락 대기 = 패킷 핸들러가 그룹을 점유한 시간
  - `t2 - t1` = 프레임 순수 작업(AI 순회 / 이동 / 확산)
- **1순위 지표 = 틱 주기 준수:** 연속 OnUpdate 시작 시각 간격 vs 목표 주기(예: 25ms).
  - 밀리기 시작(100→130→180ms)하는 것이 knee point = 유저 체감 버벅임.
  - 밀리면 `t1-t0`(락 대기) / `t2-t1`(작업)로 원인 분해.

### 집계 / 저장 방식
- **원시 샘플을 insert로 쌓지 말 것** — 초당 수천~수만 개 → 수백만 개, 락 걸고 통째 복사하면 그룹 스레드가 멈춤(관측자 효과). → 프로토콜 타입별 **누적치(count/sum/min/max)만** 유지, 락 구간은 수 ns.
- **히스토그램이 핵심(평균은 꼬리를 뭉갬):** sum/count = 평균은 분포를 중심값 하나로 붕괴시켜 꼬리(p99 = knee 신호)를 없앤다.
  - **고정 버킷 히스토그램**(로그 스케일 버킷 + 오버플로 버킷 + 별도 max)으로 분포 보존 → 누적 개수로 p50/95/99 복원. 기록 O(1), 메모리 고정.
  - min은 버린다. avg는 "avg 대비 p99 격차 = 꼬리 두께" 보너스로만.
- **컨테이너:** 프로토콜 타입 enum을 인덱스로 한 고정 배열(map 대신, 해시/할당 없음). 더블 버퍼 스왑 또는 락 + 작은 복사.
- **해상도:** 1초는 과함(현상은 분 단위, knee는 동접 단계 전환에서). **10초 버킷(soak는 1~5분)이면 충분**, 단 버킷 안은 avg 아닌 p99를 살릴 것.
  - 메인 그래프 x축 = **동접 수**(단계당 점, knee = 꺾임), 시간축은 보조(soak 드리프트용).

### 저장 3계층 (측정 오염 방지)
1. **그룹이 측정** → 자기 히스토그램에 적재
2. **모니터가 1초마다 읽어**(스왑) 넘김
3. **별도 저장 스레드가 I/O 전담(CSV)** — 모니터가 직접 파일 쓰면 측정 오염. p99 계산도 저장 스레드로 미뤄 모니터를 가볍게.
- **DBJob으로 worlddb 로그 테이블에 저장 금지** — 측정 대상 DB에 부하를 더해 결과를 왜곡한다.
- **시각:** 스냅샷(버킷)당 시각 1개(개별 이벤트마다 박지 말 것) + 그 순간 동접 수 같이. 시각 = 모니터가 읽는 "측정 시점"(저장 스레드 쓰기 시각 아님). 3도메인 공통 시계. 산발 이벤트 로그(>1s 쿼리/에러)만 줄별 발생 시각.

### 시계 선택 (오해 정정)
- "QPC는 커널 들어가 처리된 시간이 제외된다"는 **거꾸로다.**
- **QPC = 벽시계 경과 시간 전부 포함**(핸들러 + 커널 + 선점으로 안 돈 대기 + 락 대기). 아무것도 안 빠짐 → 부하 테스트에 정확히 맞다.
- 시간이 빠지는 건 QPC가 아니라 **스레드 CPU 시간 API**(GetThreadTimes = 틱 ~15ms, QueryThreadCycleTime). 이건 대기를 숨겨서 부하 테스트엔 반대로 작동(쓰면 안 됨).
- QPC는 최신 윈도우 + CPU에서 invariant TSC 기반, 유저 모드에서 끝남(시스템콜 X), 호출 ~20-30ns, 코어 간 동기화는 OS가 처리.
- **실무:** C++14이니 `std::chrono::steady_clock`(MSVC가 내부적으로 QPC를 래핑) 사용. timeGetTime(기본 ~15ms) 탈락, rdtsc 직접 호출 금지(주파수 스케일링/명령어 재배치 문제).

### 원자성 (확정)
- 카운터를 그룹에서 plain `++`(load-add-store) + 모니터가 plain `=0` 리셋이면 → 그룹의 stale store가 모니터의 0을 덮어 **리셋 유실 → 초당 값이 2배**가 되는 사고.
  - 그룹 락은 worker끼리만 막고 모니터는 그 락을 안 잡는다(잡으면 락 대기 지표가 오염됨).
- **해결: `++`를 InterlockedIncrement로.** load-add-store가 불가분이라 stale 덮어쓰기 불가(최악의 경계에서 1개 유실).
  - 모니터의 `=0`은 정렬된 mov라 그대로 OK. worker끼리는 그룹 락으로 직렬화되므로 atomic은 무경합 ~수 ns.

### 기존 카운터 점검 결과
- **네트워크 라이브러리(CLanServer/CNetServer):** `m_AcceptTPS/RecvIOTPS/SendIOTPS/CurSessionCnt`를 이미 InterlockedIncrement + 모니터 plain `=0` → **이미 안전**(= 확정한 그 패턴).
- **MMO 게임서버 FieldGroup은 plain `++`라 racy** — InterlockedIncrement 교체 권장:
  - `fieldframe` (`FieldGroup.cpp:418`, 곧 프레임 지표 = 1순위)
  - `attackCount` (`MonsterAI.cpp:251`)
  - `targetupdatePacketCount` (`MonsterAI.cpp:462`)
  - `movePacketCount` (`PacketBuilder.cpp:323`, static)
  - `stopPacketCount` (`PacketBuilder.cpp:340`, static)
  - `syncCount` (`FieldGroup.cpp:688`, 누적)
  - 전부 `GameServer.cpp` 모니터 1초 루프(146~181)가 읽고 `=0`. static 2개는 멀티 그룹 시 worker끼리도 레이스.
  - `m_syncCount`(per-user)는 단일 스레드라 안전.
