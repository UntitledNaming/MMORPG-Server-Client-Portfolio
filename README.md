# MMORPG 월드 서버

## 1. 프로젝트 개요

P1에서 직접 구현한 IOCP 네트워크·게임 라이브러리를 실제 MMORPG 월드 서버에 적용한 프로젝트입니다. C++ IOCP 기반 서버와 UE5 클라이언트가 연동되며, 서버는 AOI(관심 영역), 이동 동기화, 서버 권위 전투, 몬스터 AI, 아이템, 비동기 DB 저장을 구현했습니다. 단순 기능 구현에 그치지 않고, 최대 4000명 규모의 부하 테스트로 병목을 측정하고 원인을 분석해 개선하는 과정까지 포함합니다.

## 2. 전체 포트폴리오에서의 역할

이 프로젝트는 게임 서버 직무와 가장 직접적으로 연결되는 대표 프로젝트이자, 포트폴리오의 최종 결과물입니다. P1에서 구현·검증한 네트워크·게임 라이브러리를 실제 게임 서버에 적용한 단계입니다. 앞선 기반 기술 프로젝트에서 다룬 멀티스레드 동시성(Lock-Free)과 성능 측정·최적화 역량이, 여기서는 멀티스레드 월드 서버, 섹터 기반 AOI, DB 병목 측정·분석으로 이어집니다.

## 3. P1 네트워크 라이브러리와의 관계

- 이 레포 안에는 P1 기반의 `NetworkLib`(network_library / game_library / common_files)가 포함되어 있으며, P4 서버의 기반으로 사용됩니다.
- P1이 네트워크·게임 라이브러리의 구현과 검증이라면, P4는 그 기반 위에 실제 MMORPG 월드 서버 기능을 붙인 결과물입니다.
- P1의 게임(에코) 서버는 게임 라이브러리 검증용 서버이며, P4의 직접 전신이 아닙니다. 두 프로젝트는 같은 게임 라이브러리를 공유하는 관계입니다.

```
P1 Network/Game Library
└─ NetworkLib
   ├─ network_library     # IOCP 네트워크 코어, 세션
   ├─ game_library        # 그룹/게임 세션/유저 인터페이스
   └─ common_files        # 버퍼, TLS 메모리 풀, Lock-Free 등
        ↓  (기반으로 사용)
P4 MMORPG World Server
├─ FieldGroup             # 월드 컨텐츠 (CGroup 상속)
├─ User / Monster         # 캐릭터/몬스터
├─ Item / Inventory       # 아이템 시스템
└─ DB Job Queue           # 비동기 DB 저장
```

## 4. 핵심 구현

| 영역 | 내용 |
|---|---|
| Network / IOCP | P1 IOCP 네트워크·게임 라이브러리 기반, `FieldGroup`/`AuthGroup`이 `CGroup`을 상속 |
| FieldGroup | 월드 로직(수신 처리·프레임 로직·브로드캐스트)을 담당하는 컨텐츠 그룹 |
| AOI / Sector | 섹터 격자로 유저·몬스터·드랍을 관리하고 주변 9섹터 기준으로 시야 갱신 |
| Movement Sync | 클라이언트 입력을 받아 서버가 위치를 확정하고 주변에 브로드캐스트 |
| Combat | 서버 권위 논타겟 전투, Circle / Cone / Box 범위 판정 |
| Skill | 슬롯 기반 스킬 요청, 서버가 MP·쿨다운·사거리 검증 |
| Monster AI | Idle / Patrol / Chase / Combat / Return / Dead 상태 머신 |
| Item System | Storage·Inventory·Equipment·QuickSlot, 필드 드랍, 아이템 UID·랜덤 스탯 |
| DB Job Queue | 게임 루프와 분리된 비동기 저장, MySQL 사용 |
| Load Test / Monitoring | 최대 4000명 부하 테스트, 지연 백분위 등 지표를 CSV로 수집 |

## 5. 서버 아키텍처

```
UE5 Client
   │  (TCP / IOCP)
   ▼
GameServer
├─ NetworkLib (P1)            # IOCP 네트워크·게임 라이브러리
├─ AuthGroup                  # 접속/캐릭터 선택
├─ FieldGroup                 # 월드 로직 (AOI/전투/스킬/아이템/몬스터)
├─ DB Thread (CDBManager)     # 비동기 DB Job 처리 ──► MySQL
├─ Monitoring / Store Thread  # 지표 수집 ──► monitor.csv
└─ LoadTester (별도)          # 부하 생성 및 응답 검증
```

- 네트워크·프레임 처리는 P1 라이브러리가, 월드 컨텐츠는 `FieldGroup`이, 저장은 전용 DB 스레드가 담당하도록 분리했습니다.
- 부하 테스트는 별도 `LoadTester`가 다수의 봇으로 접속·행동을 생성하고 서버 응답을 검증합니다.

## 6. 주요 시스템

### 6.1 AOI / Sector
- 월드를 섹터 격자로 나누고 유저·몬스터·드랍 아이템을 섹터 단위로 관리합니다.
- 캐릭터·몬스터 주변 9섹터를 시야로 삼습니다.
- 섹터가 바뀌면 새로 보이는 섹터와 사라지는 섹터의 차집합만 계산해 생성/삭제 메시지를 보냅니다.
- 유저·몬스터·드랍 아이템의 시야 진입/이탈을 각각 갱신합니다.

### 6.2 이동 동기화
- 클라이언트가 좌표·yaw·moveFlag를 보내면 서버가 위치를 갱신합니다.
- 서버가 아는 위치와 차이가 임계 범위를 벗어나면 서버 좌표로 강제 보정(싱크)하고, 임계 안이면 클라이언트 좌표를 신뢰합니다.
- 확정된 이동은 주변 섹터 유저에게 브로드캐스트합니다.
- 좌표·Z축에 대한 정밀 검증 일부는 아직 구현 예정입니다. (TODO)

### 6.3 서버 권위 전투 판정
- 클라이언트는 공격 방향(yaw)과 스윙 종류, 또는 스킬 슬롯만 전송합니다.
- 피격 대상과 데미지는 서버가 판단하며, 클라이언트는 타겟 목록을 보내지 않습니다.
- 타격 범위는 Circle / Cone / Box로 나눠 판정하고, 거리·각도 비교에서 불필요한 제곱근 연산을 피했습니다.
- 데미지 계산과 HP 반영·사망·드랍·경험치 처리는 모두 서버가 수행하고, 결과를 주변 섹터에 브로드캐스트합니다.

### 6.4 몬스터 AI
- Idle / Patrol / Chase / Combat / Return / Dead 상태 머신으로 동작합니다.
- 추격 중 목표 갱신을 일정 주기와 이동량 기준으로 제한(throttling)해 이동 패킷을 줄였습니다.
- 추격과 전투 사이를 매 프레임 오가는 떨림 문제는, 전투 이탈에 재진입 여유 범위와 지연 조건을 둬서 완화했습니다.

### 6.5 아이템 / 인벤토리
- 아이템의 실체는 `Storage`가 UID로 단일 관리하고, Inventory·Equipment·QuickSlot은 슬롯에 UID만 참조로 담습니다.
- 필드 드랍 아이템은 `DropID`로 관리하고, 유저가 주워 인벤토리에 들어가는 순간 아이템 UID를 부여합니다.
- DropID와 아이템 UID를 분리한 것은 필드 드랍은 임시 개체이고 유저 소유 아이템은 영구 개체이기 때문입니다.
- 장비에는 랜덤 스탯을 부여하고 장착 시 합산해 반영합니다.

### 6.6 DB Job Queue
- 게임 루프와 DB 저장을 분리해, 컨텐츠 로직이 저장할 내용을 DBJob으로 만들어 큐에 넣습니다.
- 전용 DB 스레드가 큐에서 Job을 꺼내 MySQL에 씁니다.
- 변경된 항목만 저장(dirtyFlag), 저장 주기 조정, 여러 Job을 한 트랜잭션으로 묶는 배치를 적용해 저장·commit 횟수를 줄였습니다.

## 7. 프로토콜 설계 요약

| 프로토콜 | 설계 기준 |
|---|---|
| 이동 | 좌표·yaw·moveFlag를 받고, 서버가 싱크 임계로 검증(믿되 검증) |
| 전투 | 공격 방향·스윙(또는 스킬 슬롯)만 받고, 피격 대상·데미지는 서버가 판정 |
| 스킬 | 슬롯만 받고 MP·쿨다운·사거리는 서버가 검증, 버프/공격 응답 분리 |
| 아이템 | 클라이언트 요청은 SlotType + SlotIndex, 서버 내부 처리는 UID(UID 비노출) |
| 필드 드랍 | 필드는 DropID로 관리, 줍는 순간 아이템 UID 부여(생명주기 분리) |
| 캐릭터 초기화 | 빈 슬롯을 제외하고 사용 중인 슬롯만 가변 길이로 직렬화, 타 캐릭터는 위치 중심 |

## 9. 주요 트러블슈팅

### DB 저장 큐 폭증
- 증상: 2500명 부근에서 DB 저장 큐(dbQueue)가 계속 쌓여 발산.
- 원인: 동접 증가로 DB 저장 Job 수가 늘고, 각 Job을 처리·commit하는 과정에서 디스크 IO 부담이 커져, DB 스레드 처리량보다 enqueue 속도가 빨라짐. (특정 Job 하나가 원인이 아니라 저장 요청과 commit 비용의 누적이 원인)
- 해결: dirtyFlag로 변경분만 저장, 저장 주기 조정, 여러 Job을 한 트랜잭션으로 묶어 commit·디스크 IO 횟수를 줄임. Job별 처리시간을 분리 측정해 병목 위치를 좁힘.
- 감수한 점: commit 전에 서버가 크래시하면 해당 배치의 변경분이 롤백될 수 있고, 저장이 약간 지연될 수 있음.
- 배운 점: 병목은 특정 Job이 아니라 저장 요청·commit·디스크 IO의 구조적 누적으로 봐야 하며, Job별 처리시간 분리 측정이 원인 규명에 유효함.

### 몬스터 생성/삭제 중복 (Monster Create/Delete Duplication)
- 증상: 클라이언트에서 이미 있는 몬스터를 다시 생성하거나, 없는 몬스터를 삭제하는 상황이 관측됨.
- 원인: 섹터 경계에서 몬스터가 죽거나 리젠될 때 생성/삭제 메시지가 주변 섹터에 고르게 전파되지 않아 중복이 발생.
- 해결: 유저별 몬스터 생성/삭제 히스토리를 추적해 순서를 확인하고, 전파 대상 섹터 계산을 바로잡음.
- 배운 점: 상태가 아니라 이벤트 시퀀스를 추적해야 동시성·순서 문제가 보임.

### BadValue
- 증상: 캐릭터/아이템 로드 시 아이템 UID·개수가 이상하게 들어오거나, 드랍 아이템에 예상치 못한 값이 섞임.
- 원인: 잘못된 DB 접속 정보로 다른 DB에 연결된 경우와, 드랍 아이템 생성 시 일부 필드 초기화 누락.
- 해결: 접속 설정을 바로잡고 초기화 누락을 보완. 부하 테스터가 값 범위 이상을 와이어 레벨에서 잡도록 검증을 추가.
- 배운 점: 값 검증은 서버 로직뿐 아니라 측정 도구에서도 잡을 수 있어야 조기에 발견됨.

### Damage UnderFlow
- 증상: 전투 데미지 계산에서 값이 비정상적으로 커지거나 언더플로우가 발생.
- 원인: 장비의 공격·방어 스탯 계산 처리 문제.
- 해결: 스탯 계산 로직을 정정.
- 배운 점: 정수 연산의 경계값 처리를 전투 계산에서 특히 주의해야 함.

## 11. Build & Run

- 환경: Windows, Visual Studio 2022, C++17
- 네트워크: WinSock2 / IOCP
- 데이터베이스: MySQL
- 클라이언트: Unreal Engine 5
- 실행 요약:
  - MySQL 스키마를 준비한 뒤 게임 서버를 구동합니다.
  - UE5 클라이언트로 서버에 접속합니다.
  - 서버 IP·Port·DB 접속 정보는 Config 파일에서 설정합니다.

> P4는 Redis를 사용하지 않습니다. 저장소는 MySQL 단일 구성입니다.
> 접속 정보·DB 계정 등 민감 정보는 저장소에 포함하지 않으며, 각 환경의 Config 파일에서 직접 설정합니다.
> 자세한 설치·설정 절차는 `docs/Build_And_Run.md`로 분리합니다. (TODO)

## 12. 개선 방향

- DB 저장 정책 추가 개선(배치 크기·저장 주기의 동적 튜닝)

- 모니터링 지표의 대시보드 시각화
- 서버 재시작·복구 시나리오 강화
