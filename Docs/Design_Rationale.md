# Design Rationale

이 문서는 "왜 이렇게 설계했는지"를 정리합니다. 각 항목은 문제 상황 / 선택한 방식 / 대안 / 선택 이유 / 절충 / 검증 방법 순으로 적습니다. 코드 흐름의 상세는 `docs/Code_Flow.md`, 프로토콜은 `docs/Protocol_Design.md`를 참고하세요.

---

## 1. 왜 P1 네트워크/게임 라이브러리 기반을 사용했는가

- 문제 상황: 실제 MMORPG 서버를 처음부터 만들기보다, 검증된 기반 위에 컨텐츠를 얹고 싶다.
- 선택한 방식: P1의 `network_library`/`game_library`/`common_files`를 포함하고, `FieldGroup`·`AuthGroup`이 `CGroup`을, `CUser`가 `IUser`를 상속.
- 대안: 새 네트워크 코어를 다시 구현.
- 선택 이유: IOCP·세션·그룹·메모리 풀·Lock-Free 등 앞서 검증한 구조를 재사용해 컨텐츠에 집중하기 위함이다.
- 감수한 점: P1 라이브러리의 제약(콜백 계약, 그룹 프레임 모델)을 그대로 계승한다.
- 검증 방법: 부하·안정성 테스트로 컨텐츠까지 포함한 전체 서버를 검증.
- 관련 코드 흐름: 서버 시작/초기화, 게임 라이브러리 연동.

---

## 2. 왜 FieldGroup / Sector 구조를 사용했는가

- 문제 상황: 넓은 월드에서 유저·몬스터·드랍을 전체 스캔하면 비용이 크다.
- 선택한 방식: `FieldGroup`이 월드 컨텐츠를 담당하고, 유저·몬스터·드랍을 섹터 격자로 관리.
- 대안: 전역 리스트, 동적 공간분할(쿼드트리 등).
- 선택 이유: 격자 섹터는 좌표→인덱스 계산이 단순하고 주변 섹터 산출이 쉬워 AOI 계산을 단순화한다. 전체 스캔을 피할 수 있다.
- 감수한 점: 섹터 크기가 고정이라 상황에 맞춰 조절하기 어렵고, 경계 처리에 주의가 필요하다.
- 검증 방법: 부하 테스트에서 브로드캐스트·처리 지표 관측.
- 관련 코드 흐름: AOI/섹터 갱신.

---

## 3. 왜 AOI를 9섹터 기반으로 처리했는가

- 문제 상황: 시야에 필요한 대상만 생성/삭제하고 싶다.
- 선택한 방식: 주변 3×3(9)섹터를 시야로 삼고, 이동 시 새로 보이는/사라지는 섹터의 차집합만 갱신.
- 대안: 반경 원형 AOI, 매 프레임 9섹터 전체 재전송.
- 선택 이유: 3×3 격자는 대각 이동까지 커버하고 계산이 단순하다. 차집합으로 이동 시 중복 전송을 피해 네트워크 송신량을 줄인다.
- 감수한 점: 섹터 크기와 시야 반경이 결합되어 따로 조절하기 어렵다(섹터 크기 튜닝 필요).
- 검증 방법: 부하 테스트의 생성/삭제 브로드캐스트 지표.
- 관련 코드 흐름: AOI/섹터 갱신.
- 관련 트러블슈팅: 몬스터 생성/삭제 중복(섹터 경계).

---

## 4. 왜 이동 동기화 구조를 이렇게 잡았는가

- 문제 상황: 서버 권위를 유지하되 매 입력을 서버가 다시 계산하면 부하가 크다.
- 선택한 방식: 클라이언트가 좌표·yaw·moveFlag를 보내면, 서버가 아는 좌표와의 차이가 임계 안이면 신뢰하고, 벗어나면 강제 싱크.
- 대안: 서버 완전 시뮬레이션(입력만 받고 서버가 위치 계산), 클라 완전 신뢰.
- 선택 이유: 정상 범위 안의 클라 좌표를 믿어 연산을 줄이고, 이상치만 교정하는 타협이다. 완전 서버 시뮬레이션 대비 서버 비용을 아낀다.
- 감수한 점: 클라 좌표를 일부 신뢰하므로 임계 안 소폭 이동 조작 여지가 있고, 임계·윈도 튜닝이 필요하다. 비정상 좌표 검증 일부는 아직 미구현이다.
- 검증 방법: 3500/4000 동접에서 싱크 발생 지표 관측.
- 관련 코드 흐름: 이동 패킷 처리.

---

## 5. 왜 서버 권위 전투 판정을 사용했는가

- 문제 상황: 클라이언트가 피격 대상·데미지를 정하면 치팅이 가능하다.
- 선택한 방식: 클라이언트는 공격 방향·스윙(또는 스킬 슬롯)만 보내고, 서버가 후보 섹터를 수집해 대상·데미지·사망·경험치·드랍을 판정.
- 대안: 클라이언트가 타겟 리스트·데미지를 전송.
- 선택 이유: 클라이언트가 대상·데미지를 보내면 "안 보이는 적을 때렸다"거나 데미지를 부풀리는 조작이 가능하다. 그 정보를 아예 안 받는 것이 가장 확실한 방어다. 판정을 서버가 독점해 결과 일관성도 유지한다.
- 감수한 점: 서버 연산이 늘어난다(섹터 1차 거르기·제곱근 회피로 완화).
- 검증 방법: 부하 테스트, 안정성 테스트에서 이상 값 검출.
- 관련 코드 흐름: 전투 판정.

---

## 6. 왜 Circle / Cone / Box 판정을 나눴는가

- 문제 상황: 평타·스킬마다 타격 범위 모양이 다르다.
- 선택한 방식: 타격 도형을 원/부채꼴/직사각형으로 나눠 각각 판정.
- 대안: 원형 하나로 통일, 매번 실제 각도 계산.
- 선택 이유: 스킬별 타격 모양을 표현하면서, 논타겟 전투(대상을 지정하지 않는 방향 기반 공격)를 도형 판정으로 처리한다. 거리·각도 비교를 제곱·내적으로 정리해 제곱근·역삼각함수 호출을 피한다.
- 감수한 점: 모양별 판정 함수를 유지해야 하고, 직사각형은 로컬 좌표 변환이 필요하다.
- 검증 방법: 전투 판정 결과가 의도한 범위와 맞는지 확인.
- 관련 코드 흐름: 전투 판정.

---

## 7. 왜 몬스터 AI를 상태 머신으로 구성했는가

- 문제 상황: 몬스터 행동(대기/순찰/추격/전투/복귀)을 명확히 관리해야 한다.
- 선택한 방식: Idle / Patrol / Chase / Combat / Return / Dead 상태 머신.
- 대안: 조건 분기 뭉치, 비헤이비어 트리.
- 선택 이유: 상태별 진입/갱신을 분리하면 로직이 단순해지고 전환 조건을 명시할 수 있다.
- 감수한 점: 복잡한 행동은 상태 폭증 우려가 있다(현재는 단순).
- 검증 방법: 부하 테스트에서 몬스터 동작·패킷 관측.
- 관련 코드 흐름: 몬스터 AI Update.
- 관련 트러블슈팅: Chase ↔ Combat 떨림(전투 이탈에 재진입 여유 범위와 지연 조건을 둬서 완화).

## 8. 왜 TargetUpdate를 throttling했는가

- 문제 상황: 추격 중 매 틱 목표·이동 패킷을 뿌리면 트래픽이 폭증한다.
- 선택한 방식: 일정 주기 + 새 목표와 기존 목표 차이가 임계 이상일 때만 이동 패킷을 보냄.
- 대안: 매 틱 전송.
- 선택 이유: 네트워크 송신량을 줄이기 위함이다. 위치 갱신 민감도와 부드러움 사이의 균형을 맞춘다.
- 감수한 점: 목표 갱신이 지연되어 추격 정밀도가 소폭 낮아질 수 있다.
- 검증 방법: 부하 테스트의 몬스터 이동 패킷 지표.
- 관련 코드 흐름: 몬스터 AI Update.

---

## 9. 왜 Inventory / Equipment / QuickSlot / Storage를 분리했는가

- 문제 상황: 아이템 소유와 슬롯 배치를 함께 다루면 정합성·복잡도 문제가 생긴다.
- 선택한 방식: `Storage`가 아이템 실체(UID→아이템)를 단일 관리하고, `Inventory`/`Equipment`/`QuickSlot`은 슬롯에 UID만 담는 뷰.
- 대안: 슬롯마다 아이템 객체를 직접 보유.
- 선택 이유: 실체를 한 곳에 두면 중복 소유가 없어 정합성 유지가 쉽다. UI 슬롯(클라 요청)과 실제 아이템(서버 UID)을 분리해, 클라 요청은 슬롯 기준, 서버 내부 처리는 UID 기준으로 나눈다. UID를 클라에 노출하지 않아 조작을 막는다.
- 감수한 점: 슬롯↔Storage 두 단계 조회가 필요하다.
- 검증 방법: 부하 테스트의 아이템 사용/스왑 검증.
- 관련 코드 흐름: 인벤토리/장비/퀵슬롯/Storage.

---

## 10. 왜 FieldDropItem의 DropID와 UserItem UID를 분리했는가

- 문제 상황: 필드에 떨어진 아이템은 아직 누구 것도 아니다.
- 선택한 방식: 드랍은 `DropID`로만 관리하고, 유저가 주워 Storage에 들어가는 순간 아이템 UID를 부여.
- 대안: 드랍 생성 시점에 바로 아이템 UID 부여.
- 선택 이유: 필드 드랍은 메모리상의 임시 개체이고 유저 소유 아이템은 영구 개체라 생명주기가 다르다. 소유가 되는 순간(줍기)에 UID를 부여하는 것이 자연스럽다.
- 감수한 점: DropID와 아이템 UID 두 식별자를 관리해야 한다.
- 검증 방법: 부하 테스트의 드랍/줍기 검증.
- 관련 코드 흐름: 필드 드랍 아이템, 인벤토리.

## 11. 왜 DB 저장을 비동기 Job Queue로 분리했는가

- 문제 상황: DB 쓰기가 느려서 게임 루프에서 하면 서버가 막힌다.
- 선택한 방식: 컨텐츠가 DBJob을 만들어 큐에 넣고, 전용 DB 스레드가 처리.
- 대안: 컨텐츠 스레드가 직접 동기 쿼리.
- 선택 이유: 네트워크·프레임 스레드를 DB 지연에서 분리하기 위함이다. 부하가 증가할 때 큐 깊이를 관측해 병목을 확인할 수도 있다.
- 감수한 점: 저장이 비동기라 지연이 생기고, 크래시 시 미반영분이 유실될 수 있다.
- 검증 방법: UserCount별 부하 테스트에서 DB 큐 관측.
- 관련 코드 흐름: DB Job Queue 저장.

---

## 12. 왜 dirtyFlag / 저장 주기 조정 / 트랜잭션 배치를 적용했는가

- 문제 상황: 매 변경/매 프레임마다 저장하면 Job·commit·디스크 IO가 폭증한다.
- 선택한 방식: 변경분만 저장(dirtyFlag), 누적 타이머 주기로 저장, 여러 Job을 한 트랜잭션으로 묶어 커밋.
- 대안: 즉시 개별 저장.
- 선택 이유: 저장 Job 수와 commit 횟수를 함께 줄여 디스크 IO 부담을 낮추기 위함이다.
- 감수한 점: 커밋 전에 서버가 크래시하면 해당 배치의 변경분이 롤백될 수 있고, 저장이 약간 지연될 수 있다.
- 검증 방법: DB 큐 깊이와 Job별 쿼리 시간 측정 비교.
- 관련 코드 흐름: DB Job Queue 저장.
- 관련 트러블슈팅: DB 저장 큐 폭증.

---

## 13. 왜 DB 병목을 디스크 IO / commit 누적으로 판단했는가

- 문제 상황: 2500명 부근에서 DB 저장 큐(dbQueue)가 계속 쌓여 발산했다.
- 판단 근거(정확히):
  - 동접이 증가하면서 DB 저장 Job 수가 증가했다.
  - 각 Job을 처리·커밋하는 과정에서 개별 commit 비용이 증가했다.
  - 그에 따라 디스크 IO 부담이 커졌다.
  - DB 스레드 처리량보다 enqueue 속도가 빨라졌다.
  - 그 결과 dbQueue가 폭증했다.
  - **특정 `ItemCountUpdateJob` 하나가 근본 원인이 아니다.** ItemCountUpdateJob은 소모품 사용 경로에서 나오는 여러 저장 Job 중 하나로, 분석 대상이었을 뿐이다.
- 선택한 방식: Job별 쿼리 처리시간과 DB 스레드 단계별 시간을 히스토그램으로 측정해 병목 위치를 데이터로 좁힌 뒤, dirtyFlag·저장 주기·트랜잭션 배치로 저장·commit 횟수를 줄임.
- 대안: 특정 Job만 손보기(근본 해결이 아님).
- 선택 이유: 병목이 특정 Job이 아니라 저장 요청·commit·디스크 IO의 구조적 누적이었기 때문에, 저장 빈도와 commit 횟수 자체를 줄이는 것이 맞다고 판단했다.
- 감수한 점: 12번과 동일(롤백·저장 지연 가능성).
- 검증 방법: 개선 단계별로 dbQueue와 지표를 다시 측정.
- 관련 코드 흐름: DB Job Queue 저장.
- 관련 테스트/트러블슈팅: `docs/Test_Report.md`의 DB Queue 병목 테스트, `docs/Troubleshooting.md`의 DB 저장 큐 폭증.

> 위 설계 판단은 코드로 확인된 사실을 기준으로 정리했습니다. 일부(토큰 인증 미구현, 좌표 검증 미구현)는 부하·기능 검증 목적의 한계이며, 관련 지점은 `docs/Code_Flow.md`에 "확인 필요"로 표시했습니다.
