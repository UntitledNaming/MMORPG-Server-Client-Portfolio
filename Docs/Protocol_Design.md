# Protocol Design

이 문서는 P4 프로토콜의 설계 판단을 정리합니다. 프로토콜 목록 나열이 아니라, "클라이언트가 무엇을 보내고, 서버가 무엇을 판단하며, 왜 그렇게 나눴는지"를 중심으로 설명합니다. 상세한 바이트 구성은 `Common/Contents/ContentsProtocol.h`에 정의되어 있습니다.

패킷 ID는 대역으로 나뉩니다: Auth 0~999, Field 1000~1999, Chat 2000~2999. 각 패킷은 네트워크 라이브러리(P1) 헤더로 감싸 전송되며, 페이로드는 인코딩·체크섬으로 무결성이 확인됩니다.

핵심 원칙은 하나입니다. **클라이언트는 입력(방향·슬롯·좌표)만 보내고, 확정(대상·데미지·아이템 UID·결과)은 서버가 한다.**

---

## 1. 이동 프로토콜

- 클라이언트가 보내는 값: 위치(x/y/z), yaw, moveFlag, (별도 패킷) move mode.
- 서버가 판단하는 값: 위치 신뢰 여부(싱크 임계), 섹터 변경, 주변 유저 브로드캐스트 대상. 서버 브로드캐스트에는 서버 타임스탬프를 함께 담아 클라 보간 기준을 제공.
- 선택 이유: 좌표를 클라가 보내되 서버가 임계로 검증하는 "믿되 검증" 구조로, 클라 조작감과 서버 검증의 균형을 맞춘다. 완전 서버 시뮬레이션 대비 서버 연산을 아낀다.
- 넣지 않은 값: 속도·다음 목적지 등은 서버/클라가 yaw·moveFlag로 추정한다.
- 감수한 점: 클라 좌표를 일부 신뢰하므로 좌표 신뢰 범위를 관리해야 하고, 비정상 좌표(월드 밖·Z축 등) 검증이 필요하다(일부 미구현).
- 개선 가능성: 좌표 압축(정수 양자화), dead reckoning(추측 항법), 좌표 검증 강화.

---

## 2. 전투 프로토콜

- 클라이언트가 보내는 값: 공격 방향(yaw), 스윙 종류(swingIndex). 스킬은 스킬 슬롯.
- 클라이언트가 보내지 않는 값: 피격자 목록, 데미지 결과.
- 서버가 판단하는 값: 후보 섹터 수집, Circle/Cone/Box 판정, 데미지, 사망/경험치/드랍, 결과 브로드캐스트.
- 선택 이유: 대상·데미지를 클라가 보내면 조작이 가능하므로, 그 정보를 아예 받지 않는 것이 가장 확실한 치팅 방지다. 서버가 판정을 독점해 결과 일관성을 유지한다.
- 응답: 히트 결과는 피격 대상 수만큼 가변으로 담고, AOI(주변 섹터)에 브로드캐스트한다.
- 참고: 피격 당사자에게는 실제 HP를, 주변에는 HP 비율(ratio)만 전송한다. 즉 타 캐릭터의 정확한 HP는 동기화 대상에서 빼고, 맞을 때만 비율로 표시한다(정보 노출·트래픽 절약).

---

## 3. 스킬 프로토콜

- 클라이언트가 보내는 값: 스킬 슬롯.
- 서버가 판단하는 값: MP·쿨다운·상태·사거리 검증, 성공 여부, 버프/공격 분기, (공격 스킬이면) 피격 대상.
- 버프와 공격 스킬 처리 차이: 버프 슬롯이면 성공/시전 응답만 보내고 종료한다. 공격 슬롯이면 평타와 같은 히트 판정 처리 절차을 재사용한다.
- 결과 브로드캐스트 범위: 시전자에게 성공/실패 응답, 성공 시 주변 섹터에 시전 브로드캐스트. 공격 스킬의 피격 결과는 전투와 동일하게 AOI에 전파.
- 쿨타임을 서버가 관리한 이유: 쿨타임·MP를 서버가 관리해야 연타·무한 사용 조작을 막을 수 있다.

---

## 4. 아이템 / 인벤토리 프로토콜

- 클라이언트 요청: SlotType + SlotIndex(스왑은 From/To 각각의 SlotType+SlotIndex).
- 서버 내부 처리: 슬롯 → 아이템 UID 매핑, 실제 아이템은 Storage에서 UID로 관리.
- itemUID를 클라이언트에 직접 주지 않은 이유: UID를 노출하면 위조·추측으로 임의 아이템을 지정하는 조작이 가능하다. 클라는 슬롯으로만 지시한다.
- 슬롯 기반 요청을 사용한 이유: 클라 UI가 어차피 슬롯 단위이고, 슬롯으로 받으면 UID를 숨길 수 있다.
- 소모품 사용 응답: 성공 여부 + (성공 시) 슬롯 타입·새 개수·슬롯 인덱스.
- 장비 장착/해제 응답: 성공 여부 + 관련 슬롯·아이템 정보.
- 인벤토리/장비/퀵슬롯 이동: 스왑 요청으로 처리하고 응답은 성공 여부.
- resultCode를 넣을지 말지 판단 기준: 현재는 대부분 성공/실패(Success) 한 바이트로 최소화했다. 실패 사유(쿨타임/공간부족 등)를 세분하면 UX는 좋아지지만 프로토콜이 커진다. UI가 사유를 요구할 때 확장하는 방향이다.
- 클라이언트 예측과 서버 확정 응답 관계: 클라가 슬롯 UI를 낙관적으로 갱신하되, 서버 응답으로 확정하거나 롤백한다.

---

## 5. 필드 드랍 아이템 프로토콜

- 필드 드랍 상태: `DropID`로 관리(생성 시 DropID·아이템 종류·좌표·개수 전송).
- 유저 소유 상태: 유저가 주워 Storage에 들어가는 순간 아이템 UID를 부여.
- DropID와 ItemUID를 분리한 이유: 필드 드랍은 임시 개체, 유저 소유 아이템은 영구 개체로 생명주기가 다르다. 소유가 되는 순간에 UID를 부여하는 것이 자연스럽고, 필드 오염·중복을 막는다.
- AOI 범위 내 Create/Delete: 시야 밖 유저에게는 드랍 생성/삭제를 보내지 않아 트래픽을 아낀다.
- 줍기 처리: 클라는 DropID로 줍기를 요청하고, 서버가 인벤 수용을 확인해 성공 시 삭제 패킷·픽업 결과를 보낸다.

---

## 6. 캐릭터 생성 / 초기화 프로토콜

- 접속 후 초기화 데이터: 내 캐릭터에는 기본 정보(위치·yaw·HP·MP·레벨·경험치)와 인벤/장비/퀵슬롯을 함께 보낸다.
- 인벤토리/장비/퀵슬롯 데이터: 각 영역마다 사용 슬롯 개수(Count)를 먼저 주고, **사용 중인 슬롯만** 슬롯 인덱스·아이템 종류·개수·랜덤 스탯을 순서대로 담는다.
- 전체 고정 배열 방식과 가변 길이 방식 비교: 빈 슬롯까지 다 보내는 고정 배열은 초반처럼 슬롯 대부분이 빈 경우 낭비가 크다. 사용 슬롯만 가변으로 보내면 패킷이 작아진다.
- 구조체 통째 전송 대신 직렬화 버퍼를 사용한 이유: 구조체를 그대로 보내면 정렬/패딩·엔디안 문제와 가변 길이 데이터를 담기 어려운 문제가 있다. 직렬화 버퍼에 필요한 필드만 순서대로 쓴다.
- 빈 슬롯까지 보내지 않는 방식의 장단점: 장점은 패킷 축소, 단점은 클라가 Count 기반으로 파싱해 슬롯을 재배치해야 하는 파싱 복잡도.
- 타 캐릭터: 위치·이동 정보 중심으로만 보내고, HP·레벨·인벤은 보내지 않는다(정보 노출·트래픽 절약).

---

## 7. 프로토콜 공통 기준

- 서버 권위로 둬야 하는 값: 위치 확정(싱크), 피격 대상·데미지, 스킬 가부·쿨타임, 아이템 UID·개수, 드랍 생성/만료, 경험치·레벨.
- 클라이언트가 보내도 되는 값: 입력(좌표·yaw·moveFlag·moveMode), 공격 방향·스윙, 스킬 슬롯, 아이템 슬롯 지시.
- 클라이언트에 숨긴 값: 아이템 UID, 타 캐릭터의 정확한 HP·레벨·장비, 서버 내부 판정 근거.
- 슬롯 기반 요청을 사용한 이유: 클라 UI는 슬롯 단위이고 UID를 숨기기 위함.
- UID 기반 내부 처리를 사용한 이유: 아이템 개체를 유일하게 식별해 복제·오배치를 막기 위함.
- 가변 길이 패킷을 사용한 이유: 사용 슬롯·히트 대상 수가 가변이라 빈 공간 낭비를 없애기 위함.
- 구조체 통째 전송을 피한 이유: 정렬/패딩·엔디안·가변 길이 문제를 피하려 직렬화 버퍼를 사용.
- 패킷 크기와 직렬화 비용의 균형: 요청은 소형 고정, 응답은 필요한 만큼만 가변으로 담는다. 네트워크 헤더로 감싸 무결성을 확보한다.
- 비정상 요청 처리 기준: 범위를 벗어난 스윙/스킬 슬롯, 조작된 헤더(코드·길이·체크섬), 반복적인 싱크 폭주 시 연결을 종료한다. 좌표 값 검증 일부는 아직 미구현이다.

> 프로토콜 판단의 배경(서버 권위·치팅 방지)은 `docs/Design_Rationale.md`, 실제 처리 흐름은 `docs/Code_Flow.md`를 참고하세요.
