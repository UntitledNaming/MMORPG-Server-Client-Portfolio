## 1. DB 저장 큐 폭증

- 증상: 2500명 부근에서 DB 저장 큐(dbQueue)가 계속 쌓여 발산.
- 초기 가설: 특정 저장 Job(예: 소모품 사용에서 나오는 아이템 개수 변경 Job) 하나가 큐를 채우는 것으로 의심.
- 분석 과정:
  1. Job별 쿼리 처리시간과 DB 스레드 단계별 시간(대기·꺼내기·실행·되돌리기·삭제)을 히스토그램으로 측정.
  2. 특정 Job 하나만 과도한 것이 아니라, 동접이 늘면서 저장 Job 전체가 늘고 각 Job의 커밋·디스크 IO가 누적되는 구조임을 확인.
  3. DB 스레드 처리량보다 enqueue 속도가 빨라지는 지점에서 큐가 발산함을 확인.
- 원인: **동접 증가 → DB 저장 Job 증가 → 개별 commit 비용 증가 → 디스크 IO 증가 → DB 스레드 처리량 부족 → dbQueue 폭증.** 특정 `ItemCountUpdateJob` 하나가 근본 원인이 아니라, 저장 요청·commit·디스크 IO의 구조적 누적이 원인.
- 해결: 변경분만 저장(dirtyFlag), 저장 주기 조정, 여러 Job을 한 트랜잭션으로 묶는 배치를 적용해 저장·commit·디스크 IO 횟수를 줄임.
- 결과: 개선 단계별로 dbQueue 발산이 완화됨
- 배운 점: 병목은 눈에 띄는 특정 Job이 아니라 저장 구조 전체의 누적으로 봐야 함.
- 관련 문서/로그: `Server/Docs/.../측정 자료/UserCount_2500/`(단계별 개선 자료), `docs/Test_Report.md` DB Queue 병목 테스트.

## 2. Monster Create/Delete Duplication

- 증상: 더미 클라이언트에서 이미 있는 몬스터를 다시 생성하거나, 없는 몬스터를 삭제하는 상황이 관측됨.
- 초기 가설: 섹터 경계 좌표(예: 0,0)에서 주변 섹터 계산이 어긋나 생성/삭제가 겹치는 것으로 의심.
- 분석 과정:
  1. 유저마다 어떤 몬스터에 대해 생성/삭제 패킷을 보냈는지 그 순간의 상태만으로는 알 수 없어, 몬스터별 생성/삭제 **히스토리**를 기록해 순서를 추적.
  2. 히스토리를 보니, 몬스터가 죽어 삭제되어야 할 시점에 삭제가 주변 섹터에 고르게 전파되지 않았고, 이후 리젠 시 생성이 중복될 수 있는 상황을 확인.
  3. 몬스터가 죽은 뒤 삭제 패킷을 보낼 때, 몬스터가 있는 섹터에만 여러 번 보내고 주변 섹터에는 안 뿌려 중복·누락이 생김을 확인.
- 원인: 섹터 경계·전파 대상 섹터 계산의 불일치로 생성/삭제 메시지가 고르게 전파되지 않음.
- 해결: 전파 대상 섹터 계산을 바로잡고, 히스토리 추적으로 순서를 검증.
- 결과: 중복 생성/삭제가 해소됨.
- 배운 점: 락프리에서 사용한 검증 방법이 많은 상황에서 유효함.
- 관련 문서/로그: `Server/Docs/.../안정성 테스트/Monster Create_Delete Duplication/`.

## 3. BadValue (스탯 매핑 실수)

- 증상: 부하 도구의 값 범위 검증에서 몬스터 공격력이 비정상 값으로 검출(BadValue). 설계값은 ATK 1~3·2~4인데 13·26·29 등이 관측되고, DB에는 17이 저장되어 있었다.
- 초기 가설: 데미지 공식이나 로드 파싱의 문제로 의심.
- 분석 과정:
  1. 값이 만들어져 흐르는 경로(생성 → DB 저장 → 로드 → 전파)를 따라 어느 단계에서 어긋나는지 추적.
  2. 설계값과 DB 저장값이 이미 다른 것을 확인 → 저장 시점에서 값이 틀어졌다고 좁힘.
  3. DB 저장 Job을 만들 때 컬럼 매핑이 어긋나 있음을 확인.
- 원인: DB 저장 Job의 컬럼 매핑 실수 — max_hp를 atk에, max_mp를 def에 넣고 있었다.
- 해결: 컬럼 매핑을 바로잡음. 아울러 부하 도구가 값 범위 이상(스탯·HP 범위 밖 등)을 와이어 레벨에서 잡도록 검증을 추가.
- 결과: 스탯이 설계값 범위로 정상화되고, 이후 유사 문제를 부하 도구가 조기에 검출.
- 배운 점: 값이 흐르는 경로(생성→저장→로드→전파)를 따라 추적해야 어느 단계의 실수인지 보임.
- 관련 문서/로그: `Server/Docs/.../안정성 테스트/BadValue/`, `Server/Docs/.../부하 및 안정성 테스트 버그 및 해결.txt`.

## 4. HP BadValue (미초기화)

- 증상: 부하 도구의 값 범위 검증에서 HP가 비정상 값으로 검출(BadValue). 데미지 계산 결과가 어긋나 HP가 정상 범위를 벗어남.
- 초기 가설: 데미지 공식 자체의 문제로 의심.
- 분석 과정:
  1. 데미지가 튀는 상황의 값을 추적 → 데미지 계산에 들어가는 장비의 공격·방어 스탯을 확인.
  2. 해당 스탯이 초기화되지 않은 채(멤버 변수 미초기화) 계산에 사용되고 있음을 확인.
- 원인: 공격·방어 스탯 미초기화 — 초기화되지 않은 값이 데미지 계산에 들어가 HP가 비정상 범위로 계산됨.
- 해결: 초기화 누락을 보완.
- 결과: HP·데미지가 정상 범위에서 계산됨.
- 배운 점: 멤버 변수 초기화 누락은 값 범위 이상으로 드러나므로 초기화를 빠뜨리지 않도록 주의한다.
- 관련 문서/로그: `Server/Docs/.../안정성 테스트/`.

## 5. 몬스터 Chase / Combat 떨림

- 증상: 몬스터가 추격(Chase)과 전투(Combat) 상태를 매 프레임 오가며 떠는 현상.
- 초기 가설: 상태 전환 조건이 같은 경계값을 쓰고 있어서로 의심.
- 분석 과정:
  1. 전투 진입은 공격 범위 안, 전투 이탈은 같은 범위 밖으로 판정하면, 경계 근처에서 매 프레임 진입/이탈이 반복됨을 확인.
- 원인: 전투 진입·이탈 판정이 같은 경계를 사용해, 경계 근처에서 상태가 진동.
- 해결: 전투 이탈 판정에 그 범위를 벗어난 상태가 일정 시간 지속돼야 추격으로 전환하도록 반경 여유를 적용.
- 결과: 경계 근처에서 상태 진동이 사라짐.
- 배운 점: 임계 기반 상태 전환은 진입·이탈에 여유(반경 여유)를 둬야 진동을 막을 수 있다.
- 관련 문서/로그: 몬스터 AI 코드(`MonsterAI.cpp`).

## 6. 타 캐릭터 스냅샷 보간 

- 증상: 다른 캐릭터가 부드럽지 않게 보이거나(끊김), 순간적으로 뒤로 튀는(역행) 등 렌더링 문제.
- 분석 과정:
  1. 서버는 위치·목적지 스냅샷과 서버 타임스탬프를 보내고, 실제 부드러운 표현은 클라이언트가 스냅샷 사이를 보간해 만든다는 점을 확인.
  2. 보간 시 스냅샷 간격·지연 버퍼 처리에 따라 역행·과도 예측(외삽)이 생길 수 있음을 확인.
- 원인: 보간/역행/외삽은 서버가 준 스냅샷을 클라이언트가 렌더링하는 과정의 문제로, 서버 로직이 아니라 클라이언트 표현 영역에 가깝다.
- 해결: 서버는 위치·목적지 스냅샷과 타임스탬프를 일관되게 제공하고, 보간 처리는 클라이언트에서 다룬다.
- 결과: 서버는 스냅샷 제공에 집중하고, 표현 개선은 클라이언트 과제로 분리.
- 배운 점: 서버는 권위 위치와 목적지를 제공하고 표현은 클라에 위임한다는 역할 분담을 명확히 해야 한다.
- 관련 문서/로그: 이동/브로드캐스트 코드(`FieldGroup.cpp`, `PacketBuilder.cpp`).
- 확인 필요: 보간/역행/외삽의 실제 구현은 이 레포의 서버 소스 범위 밖(UE5 클라이언트)이다.

## 7. 3500명 Sync 폭증

- 증상: 동접 3500명 부근부터 Sync(위치 강제 보정) 카운트가 급증. 모니터링에서 SyncCount 폭증과 함께 더미 클라이언트 머신의 TCP 재전송 증가가 함께 관측됨.
- 초기 가설: 좌표 검증 임계나 이동 로직 자체의 문제로 의심.
- 분석 과정:
  1. 재전송·Sync 지표를 함께 관측 → 메시지를 낱개로 send하면서 세그먼트 수가 폭증함을 확인.
  2. 고동접에서 과다한 세그먼트가 TCP 재전송을 유발하고, 전달 지연으로 서버·클라 좌표 차이가 싱크 임계를 넘김을 확인.
- 원인: 과다한 세그먼트 → TCP 재전송 → 전달 지연 → 서버·클라 좌표 차이 확대 → Sync 급증.
- 해결: Send 전용 스레드를 두고 세션별로 쌓인 메시지를 모아 한 번에 전송해 세그먼트 수를 줄임.
- 결과: TCP 재전송과 Sync가 함께 감소. 4000명에서 남는 일부 Sync는 더미(봇)의 보정 처리 누락에 의한 것으로 확인.
- 배운 점: 높은 동접에서는 보내는 바이트양만이 아니라 세그먼트 수 자체가 병목이 된다.
- 관련 문서/로그: `Server/Docs/.../안정성 테스트/`, `docs/Test_Report.md`.
