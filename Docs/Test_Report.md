## 3. DB Queue 병목 테스트

- 관측: 2500명 부근에서 DB 저장 큐(dbQueue)가 계속 쌓여 발산했다.
- 원인(정확히):
  - 동접 증가에 따라 DB 저장 요청(Job)이 증가했다.
  - 각 Job을 처리·커밋하는 과정에서 개별 commit 비용이 증가했다.
  - 그에 따라 디스크 IO 부담이 커졌다.
  - DB 스레드 처리량보다 enqueue 속도가 빨라져 큐가 폭증했다.
- 분석 방법: Job별 쿼리 처리시간과 DB 스레드 단계별 시간을 측정해 병목 위치를 데이터로 좁혔다. `UserCount_2500` 아래에 쿼리 시간 측정 추가, DB 스레드 시간 측정 추가, 저장 Job 수 조정, 트랜잭션 배치 등 단계별 개선 자료가 있다.
- 개선: dirtyFlag로 변경분만 저장, 저장 주기 조정, 여러 Job을 한 트랜잭션으로 묶는 배치를 적용해 저장·commit 횟수를 줄였다.
- 주의: `ItemCountUpdateJob`은 소모품 사용 경로에서 나오는 여러 저장 Job 중 하나로 분석 대상이었을 뿐, 이 Job 하나가 근본 원인이 아니다. 병목은 저장 요청·commit·디스크 IO의 구조적 누적이었다.
- 개선 전후 dbQueue 정량 값은 CSV 판독 후 채웁니다. (TODO)

## 4. 부하 테스트 지표

측정 스냅샷(`monitor.csv`)과 부하 도구에서 관측하는 지표는 다음과 같습니다.

- user count(동접)
- dbQueue(DB 저장 큐 깊이)
- recv/send 처리량
- TCP 재전송(PDH)
- 싱크 관련 지표(서버가 강제 보정한 횟수 등)
- CPU / 메모리(PDH)
- 지연 백분위(p50/p95/p99/p999/max) — 수신 처리·프레임·브로드캐스트·DB Job별
- LoadTester 지표: 접속 성공/리셋, 송수신 패킷·바이트, RTT, 오류 종류별 카운트

## 5. 결론

- 단순 기능 구현에 그치지 않고, 최대 4000명 규모의 부하를 걸어 병목을 관측했다.
- DB 저장 경로에서 큐가 발산하는 지점을 찾고, 원인을 저장 요청·commit·디스크 IO의 누적으로 분석해 dirtyFlag·저장 주기·트랜잭션 배치로 측정 기반으로 개선했다.
- 부하 도구가 서버 응답을 와이어 레벨에서 검증하고, 서버가 지연을 백분위로 남기는 모니터링 설계를 통해 서버 상태를 데이터로 확인했다.

> 안정성 문제의 재현·해결 과정은 `docs/Troubleshooting.md`를 참고하세요.
